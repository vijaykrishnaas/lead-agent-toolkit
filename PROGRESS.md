- **Real security bug found and fixed — task 19's own fix doesn't actually close the spoofing gap it was written for, because the "secret" marker is posted in plain text.** `reviewer/src/github/postReviewComment.js`'s `findExistingBotComment` walks a PR's comments (oldest-first) and keeps overwriting `found` with every marker-prefixed match, so the *most recent* match wins. Task 19 replaced the fixed public marker string with `computeBotCommentMarker`, an HMAC of `owner/repo#prNumber` keyed by the caller's GitHub token, reasoning that this makes the marker "unpredictable to anyone without that credential" — but `findExistingBotComment` itself was untouched, and the marker is prepended as plain text to the start of every comment the tool posts (`markedBody = `${computeBotCommentMarker(...)}\n${body}``), so it is fully readable — and therefore copyable verbatim — by anyone who can read the PR's comments, which is exactly the access level task 19's own threat model (a non-owning PR commenter) already assumes. An attacker never needs to know or guess the HMAC key; they only need to read one genuine bot comment and paste its marker onto a new comment of their own. Reproduced directly: mocked a PR with a genuine bot comment (id 101, the real computed marker) followed by a second, later comment (id 102) whose body starts with that same marker text copied verbatim — `postReviewComment`'s next run `PATCH`ed comment 102, not 101, with zero knowledge of the token. This is precisely "permanently orphaning the real comment," the exact failure task 19's own PROGRESS.md/TASKS.md entries describe as the bug being fixed — undone by a search-order assumption (last-match-wins) inherited unchanged from the pre-HMAC design and never re-examined against the new threat model once the marker itself became attacker-copyable rather than attacker-guessable.
  - Fix: switched `findExistingBotComment` to return the *first* (oldest) marker-matching comment and stop searching, instead of the last. This closes the gap because a copy can only ever be posted after the genuine comment it copies from already exists — so the earliest match in a marker-prefixed thread is always the genuine one, and a later copy is simply never selected as canonical, no matter how many are posted.
  - Updated the existing "updates the most recent bot comment when more than one exists" test to assert the corrected "earliest wins" behavior instead (verified this is a deliberate, evidence-backed behavior change, not an accidental test weakening). Added a new `SECURITY:` regression test reproducing the exact copy-attack scenario above (older genuine comment id 101, newer copied-marker comment id 102, asserts 101 is the one `PATCH`ed) — confirmed to fail against the pre-fix code (asserted, then reverted just `postReviewComment.js` via `git stash`, reran, watched it fail with the PATCH targeting comment 102, then restored the fix and reran to green) and pass against the fix.

## 2026-07-19 (task 19: HMAC-keyed bot-comment marker)

**Done:** Task 19 — `reviewer/src/github/postReviewComment.js`'s bot-comment identification no longer relies on the fixed public string `BOT_COMMENT_MARKER`. Replaced it with `computeBotCommentMarker(token, owner, repo, prNumber)`, which derives a per-PR suffix as `crypto.createHmac('sha256', token).update(`${owner}/${repo}#${prNumber}`).digest('hex').slice(0, 16)` appended to a public prefix (`BOT_COMMENT_PREFIX`), exactly as proposed in TASKS.md 19 / RETRO.md 2026-07-19 self-audit round 3. Both `findExistingBotComment` (the marker it `startsWith`-matches against) and `postReviewComment` (the marker it prepends when posting/updating) now compute this per-call from the caller's own token instead of importing the old constant. `BOT_COMMENT_MARKER` is no longer exported; `BOT_COMMENT_PREFIX` and `computeBotCommentMarker` are exported in its place.

- Why this closes the spoofing gap: a non-owning PR commenter without the repo owner's/Action's GitHub token cannot reproduce the HMAC suffix for a given `owner/repo#prNumber`, so a comment they post starting with just the public prefix (no valid suffix, or a guessed one) no longer `startsWith`-matches the real marker and is correctly ignored — verified with a new test (`does not treat a spoofed comment using a fixed public prefix (no valid HMAC suffix) as a prior bot comment`) that posts a comment body starting with `${BOT_COMMENT_PREFIX} -->` (the old, now-inert fixed marker) and confirms `postReviewComment` still POSTs a new comment instead of PATCHing the spoofed one.
- No `GET /user` call added (would break the default `GITHUB_TOKEN` credential in GitHub Actions, per the post-task-16 PROGRESS.md entry) and no `comment.user.type === 'Bot'` check added (would break PAT-based local usage) — the fix needs no extra API call at all, per the task's own proposal.
- A token rotation between runs is still a graceful fallback, not a regression: the new marker for the same PR is simply different, so `findExistingBotComment` finds nothing and `postReviewComment` posts a fresh comment — the same "no prior comment found" path that already existed for a PR's first-ever run.
- Updated `reviewer/tests/github/postReviewComment.test.js`: every existing fixture that hardcoded `BOT_COMMENT_MARKER` now uses a `marker` computed once per `describe` block via `computeBotCommentMarker(baseArgs.token, baseArgs.owner, baseArgs.repo, baseArgs.prNumber)`, so the existing find/PATCH/paging/mid-body tests keep proving the same behavior against the new marker shape. Added 5 new tests: the spoofed-fixed-prefix case above, plus a `computeBotCommentMarker` unit-test block covering determinism (same inputs → same marker), token-sensitivity (different token → different marker, the core unpredictability property), and cross-PR/cross-repo uniqueness (different `prNumber` or `repo` → different marker, so a captured marker from one PR can't be replayed onto another).
- Did not touch `reviewPrCli.js` — it already treats `postReviewComment`'s return value opaquely (via `result.updated`, from task 16) and never referenced `BOT_COMMENT_MARKER` directly, so no caller-side change was needed.

**Test run:** `reviewer/` 266/266 green (261 pre-existing + 5 new, all in `postReviewComment.test.js`); `sample-app/` 44/44 green, unaffected by this task. Both suites needed a fresh `npm install` this run (no `node_modules` present in this checkout).

**Decisions:**
- Kept the public prefix (`BOT_COMMENT_PREFIX = '<!-- lead-agent-toolkit:review-pr'`) visible and unchanged in shape from the old marker's leading text, rather than making the entire marker opaque — a human skimming raw PR comment HTML can still recognize "this is the review-pr bot" without needing to know the HMAC scheme; only the part that needs to be unguessable (the suffix) is secret-derived.
- Used `slice(0, 16)` of the hex digest (64 bits) exactly as proposed in TASKS.md, rather than the full 256-bit digest — long enough that guessing without the token is infeasible, short enough to keep the marker line short in rendered comment source.
