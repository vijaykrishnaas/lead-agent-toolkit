# Skill Changelog

## 2026-07-19 (self-scheduled routine run 3)
**Change:** Added two new guidelines to CLAUDE.md (below the hard invariants). First: a statement/brace-body boundary walk whose continuation check is "does this line look like a valid continuation of the construct" must treat a blank or comment-only line as a non-terminating continuation, never as proof the construct ended, and such a walk's tests must include a comment-only/blank line inserted between two real lines of the same construct. Second: a check that tests a collected block/window for a keyword marker's presence or absence must test the string/comment-masked version of that text, never the raw text, since a comment or string literal merely mentioning the marker can spoof the check in either direction; such a check's tests must include the marker's literal text appearing only inside a comment, with no real occurrence.

**Evidence:** PROGRESS.md, 2026-07-19 "self-scheduled routine run 3" entry — with all 19 TASKS.md items `[DONE]` and no topmost non-DONE item, this run continued the precedent established by runs 5-7 and the two prior self-scheduled routine runs (hunt the newest not-yet-independently-reviewed diff, `6764bae`). That hunt found no new bug in `6764bae`'s own change (comment-masking in `maskStringLiterals`), but tracing through how `errorHandling.js`/`performance.js` actually consume the now-comment-aware masked text surfaced two distinct, real, previously-unfound bugs, both predating `6764bae` itself (confirmed by reproducing each against the immediately prior commit's code before making any change), neither caught by any of the several prior adversarial-hunt rounds that read these exact files:
1. `collectStatement`/`handlerHasBraceBody`'s continuation check (`!masked.trim().startsWith('.')`) treated a comment-only line the same as an unrelated next statement, truncating the scan before reaching a chain's real `.catch()` or a handler's real `{` body — reproduced as both a false positive (caught chain flagged as uncaught) and a false positive (guarded handler flagged as unguarded). Fixed by skipping blank/comment-only lines in both functions' continuation checks instead of breaking on them.
2. `errorHandling.js`'s `TRY_BLOCK`/`ASYNC_WRAPPER`/`CATCH_CALL` and `performance.js`'s `AWAIT_PATTERN` all tested the *raw* collected block/window text, not the masked text `collectBoundedBlock`/`collectStatement` already compute internally for their own depth-counting — reproduced as a false negative (a comment mentioning "try {"/"asyncHandler" silenced a genuinely-unguarded-handler finding; a comment mentioning ".catch(" silenced a genuinely-uncaught-chain finding) and a false positive (a comment mentioning "await" flagged a genuinely-clean forEach). Fixed by masking the already-collected block/window once more at each of the three call sites before testing the regex.

6 new regression tests total (3 for bug 1, 3 for bug 2), all confirmed via `git stash` to fail against the pre-fix code and pass against the fix. `reviewer/` suite 288 → 294 green; `sample-app/` unaffected, 48/48. All 19 `TASKS.md` items remain `[DONE]`.

## 2026-07-19 (self-scheduled routine run 2)
**Change:** Broadened the CLAUDE.md string-literal-aware depth-counting guideline (below the hard invariants) for a second time — generalized "a string or template literal" to explicitly name `//` line comments and `/* */` block comments as their own non-structural-text category that must also be masked before any brace/paren depth count, and required each such depth-counting helper's test suite to cover opening- and closing-shaped-character cases for all three categories (string/template literal, line comment, block comment), not just whichever one prompted the most recent fix.

**Evidence:** PROGRESS.md, 2026-07-19 "self-scheduled routine run 2" entry — `reviewer/src/utils/maskStringLiterals.js` (the shared helper this guideline itself caused to be built) masked string/template-literal content but never comments. None of `maskStringLiterals.test.js`'s existing cases exercised comments at all — the guideline's own prior wording ("a string or template literal") never named comments as a category needing the same treatment, which is why a helper built specifically in response to this guideline still shipped without it. Fixed by extending `maskStringLiterals` to mask `//` line comments (bounded to the next newline, since `docDrift/parseExpressRoutes.js` passes a whole multi-line file as a single `content` string in one call — a comment must not mask past its own line) and `/* */` block comments (including multi-line ones, threaded via the same `quoteState` value already used for multi-line template literals, using a new `/*` sentinel value). 7 new regression tests (5 in `maskStringLiterals.test.js`: single-line `//`, a `//` bounded within a multi-line `content` string, single-line `/* */`, a `/* */` threaded across two calls, and a `//`-inside-a-string-literal case confirming comment detection doesn't fire inside an already-open quote; 2 in `errorHandling.test.js` mirroring the existing "brace on next line" regression pair — one confirming the false positive is gone, one confirming a genuinely-unguarded handler with the same trailing-comment shape is still flagged, so the fix doesn't overcorrect). Verified against the real `sample-app/` source tree (not just synthetic fixtures) that `docDrift/parseExpressRoutes.js`'s route extraction is unaffected by the multi-line-`content`-string comment handling. `reviewer/` suite 281 → 288 green (7 net-new); `sample-app/` unaffected, 48/48. ## 2026-07-19 (self-scheduled routine run)
**Change:** Broadened the existing CLAUDE.md per-occurrence-scoping guideline (below the hard invariants) for a seventh time — added a general sentence warning that deciding an occurrence's *shape* (block-bodied vs. brace-less, etc.) by inspecting only its own starting line is unsafe whenever the deciding token can legally land on a later line, and that the shape-classification check must scan forward the same way the boundary-derivation helper it feeds into would, checking for the deciding token before applying any early-exit condition — not just re-derive the boundary correctly once the shape is already (mis)decided.

**Evidence:** PROGRESS.md, 2026-07-19 "self-scheduled routine run" entry — `reviewer/src/rules/errorHandling.js`'s brace-vs-brace-less classification (added in the immediately preceding run, adversarial-hunt run 7, commit `7602cc3`, to fix the sixth recurrence of this guideline's bug class) checked only `addedLines[idx].content` — the handler's own signature line — for an opening `{`. A block-bodied arrow handler can legally put its `{` on the line *after* the signature (`async (req, res) =>` then a bare `{` on the next line), which that check misclassified as brace-less. Misrouted to `collectStatement`, whose break condition ("depth back to 0, line isn't a `.`-continuation") fires the instant it reaches the bare `{` line — before ever reaching a try/catch nested inside — so a fully try/catch-wrapped handler was misflagged as missing error handling. Reproduced directly with a standalone repro script before touching any code: `exports.getWidget = async (req, res) =>` / `{` / `  try { ... } catch (err) { ... }` / `};` produced a false-positive finding against fully compliant code. None of `errorHandling.test.js`'s existing cases — including run 7's own two new brace-less-handler tests — put the opening `{` on a line after the signature, so this shape was never exercised. This is the seventh recurrence of the file's own per-occurrence-scoping/boundary-derivation bug class (see CLAUDE.md's guideline for the full six-recurrence trail run 7 itself was the sixth entry in), in a genuinely new trigger shape none of the prior six fixes' evidence considered: not the boundary derivation itself being wrong, but the up-front *classification* of which boundary derivation to use being wrong, based on checking only one line instead of scanning forward. Fixed by replacing the starting-line-only check with a new `handlerHasBraceBody` helper that walks the same statement-boundary lines `collectStatement` scans, checking each line for `{` before applying `collectStatement`'s own break condition — a companion regression test (handler with no try/catch, brace on the line after the signature) confirms the fix doesn't overcorrect into never flagging this shape at all. Both new tests confirmed to fail/pass correctly against pre-fix/post-fix code via `git stash`. `reviewer/` suite green throughout (279 -> 281, both net-new in `errorHandling.test.js`); `sample-app/` unaffected (48/48). ## 2026-07-19 (adversarial bug-hunt run, post-task-19)
**Change:** Added a new guideline to CLAUDE.md (below the hard invariants) requiring that a marker/identifier a tool posts into public or shared output, then reads back to recognize its own prior content, never be treated as a secret once posted — even if derived from a secret via HMAC — since anyone who can read the output can copy the marker verbatim, and requiring "find my prior occurrence" searches to prefer the *earliest* matching occurrence rather than the most recent one, since a copy can only ever be posted after the genuine original it copies.

**Evidence:** PROGRESS.md, 2026-07-19 "adversarial bug-hunt run, post-task-19" entry — task 19 (HMAC-keyed bot-comment marker, commit `4ed98ce`) shipped with no adversarial hunt yet run against it. `reviewer/src/github/postReviewComment.js`'s `findExistingBotComment` kept its pre-task-19 last-match-wins search unchanged, even though task 19's own stated threat model (a non-owning PR commenter spoofing the marker to hijack future updates) is defeated by exactly that search order: the HMAC-derived marker is posted as plain text at the start of every comment the tool writes, so it's readable — and copyable — by anyone who can read the PR's comments, the same access level the threat model already assumes an attacker has. Reproduced directly: a genuine bot comment (id 101) followed by a second, later comment (id 102) that merely copied the real marker text verbatim caused `postReviewComment` to `PATCH` comment 102 on the next run instead of 101, permanently orphaning the real comment — the exact failure task 19 was written to prevent, with no knowledge of the GitHub token required to pull off. Fixed by switching `findExistingBotComment` to return the first (oldest) marker match instead of the last. 1 new regression test (older genuine comment + newer copied-marker comment, asserts the older one is PATCHed, confirmed to fail against the pre-fix code and pass against the fix) plus 1 existing test's expectation corrected from "most recent wins" to "earliest wins."
