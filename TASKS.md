Make `findExistingBotComment`'s bot-comment identification resistant to spoofing by a non-owning PR commenter, without relying on a `GET /user` call (breaks the default `GITHUB_TOKEN` credential in GitHub Actions, per the post-task-16 PROGRESS.md entry) or a `comment.user.type === 'Bot'` check (breaks PAT-based local usage, since a human operator's own token posts as `type: 'User'`). Proposed fix: derive `BOT_COMMENT_MARKER`'s suffix per `owner/repo/prNumber` from an HMAC keyed by the GitHub token itself (e.g. `crypto.createHmac('sha256', token).update(`${owner}/${repo}#${prNumber}`).digest('hex').slice(0, 16)`) instead of a fixed public string — unpredictable to anyone without the token, needs no extra API call, and works identically for `GITHUB_TOKEN` and PAT credentials alike. A token rotation between runs would just miss the old comment and post a new one (graceful fallback, same as today's "no prior comment found" path), not a regression. (Proposed in RETRO.md, 2026-07-19 self-audit round 3 — raised in the post-task-16 hunt, re-analyzed with an escalated impact in the following adversarial-hunt run (spoofing can permanently orphan the real bot comment, not just self-limited griefing), and deferred twice for lack of a fix without a compatibility cost; this HMAC-based marker is the first proposed fix that avoids both previously-identified costs.)
