## 1. Async Express error handling

Async Express route handlers must never let a rejected promise reach the client unhandled — wrap with an async-error handler (e.g. `src/middleware/asyncHandler.js`) and route errors to a catch-all error middleware. Every handler's test suite must include at least one rejected-promise case, not only resolved-happy-path mocks. (Evidence: PROGRESS.md 2026-07-17 adversarial-hunt run — `usersController`/`tasksController` had no error handling; a rejected model call hung the request indefinitely, undetected by 25 happy-path-only tests.)


## 2. Per-occurrence scoping and structural boundary derivation

Diff-scanning static-analysis rules (in `reviewer/src/rules/*` and, later, `review-rules.yaml`) must scope pattern checks to the local block/occurrence being evaluated, never aggregate a single boolean across a whole file diff OR across multiple files in the same diff — one compliant instance (a try/catch, a `.catch()`, a matching test file) must not silence findings for a different non-compliant instance, whether in the same file or a different file changed in the same diff. This violation isn't only the obvious `hasX`-computed-once-and-reused shape — a single regex `.test()`/match against a *joined/combined multi-line string* of all added lines (e.g. `lines.map(l => l.content).join('\n')`) is the same violation wearing a different shape, since it lets an occurrence in one block satisfy (or get blamed for) a pattern that actually belongs to a different, unrelated block. Any check that needs to reason across multiple lines of one occurrence must extract that occurrence's own bounded block first (e.g. brace-depth tracking from its opening `{` to its matching `}`, as `errorHandling.js` and the `performance.js` fix below do) before testing it — never regex a same-file-wide joined blob. Every such rule's test suite must include a multi-occurrence case (2+ handlers/chains/blocks in one file, or 2+ source files in one diff, mixed compliant/non-compliant) — a single-occurrence test cannot catch this class of false negative, and when auditing an existing rule for this bug class, explicitly check for `join('\n')`/combined-string regex tests, not just reused boolean flags. Extracting a bounded per-occurrence block is necessary but not sufficient: the block's boundary itself must be derived from the code's actual structure (brace depth, paren depth, or a statement-terminating `;`), never an arbitrary fixed-size line window — a window that's too small can miss a real `.catch()`/`try`/etc. that's genuinely part of the same occurrence a few lines further down (false positive), while a window that's too large can pull in an unrelated, independent occurrence's compliant marker and silence a genuinely non-compliant one right next to it (false negative). "The next occurrence's own start" (e.g. the next handler signature, the next `.route()` call) is *not* a safe substitute for the occurrence's own structural end unless something already guarantees nothing else can appear in between — real code regularly has unrelated statements, helper functions, or other non-occurrence content sitting between two occurrences of the same construct, and using the next occurrence's start as a boundary sweeps that unrelated content's own compliant markers (e.g. its own unrelated try/catch) into the current occurrence's block, silencing a genuinely non-compliant occurrence. Prefer the occurrence's own brace/paren-depth end every time one exists; only fall back to "next occurrence's start" when the construct genuinely has no structural closing token of its own to track. A brace-depth-bounding helper that degrades to "read to the end of input" when no opening `{` is ever found (a reasonable fallback for a construct that always has one) must never be applied to an occurrence whose own detection pattern doesn't guarantee an opening `{` is present on the line being scanned from — a signature-only regex (e.g. matching `async (req, res)` without requiring the following token be `{`) can match a brace-less/concise-body construct just as validly as a block-bodied one, and handing that occurrence to the brace-hunting helper triggers its degenerate fallback, sweeping every following line — including a different, unrelated occurrence's own compliant marker — into the window. Before reusing such a helper for a new occurrence shape, check whether that shape's detection pattern can match a construct with no opening token at all; if it can, that shape needs its own statement-boundary derivation (paren-depth plus a terminating `;`, or "next line isn't a continuation") instead. Deciding an occurrence's shape (brace-bodied vs. brace-less, block vs. statement, etc.) by inspecting only its own starting line is the same class of bug in yet another guise: real formatting styles routinely put the deciding token (an opening `{`, an operator, a keyword) on a line *after* the occurrence's signature/header line, so a starting-line-only check misclassifies a construct that is actually the "correctly-boundable" shape as the "needs a different, narrower boundary derivation" shape — and if that narrower derivation's own break condition doesn't re-check for the deciding token on every subsequent line before applying its break/end logic, it can terminate before ever reaching the real body, producing a false positive against fully compliant code. The shape-classification check itself must scan forward across the same lines the boundary derivation would scan, not just the occurrence's first line, checking for the deciding token before applying any early-exit condition. Every such rule's test suite must therefore include both a multi-line-formatted-but-compliant case (to catch the too-small-window false positive) and an adjacent-independent-occurrences case with *unrelated, non-occurrence content* in between (to catch both the too-large-window false negative and the next-occurrence's-start false negative), not just a same-line-or-tight-window case or two occurrences with nothing but whitespace between them. ## 3. Testable entry points must guard every pipeline stage

A script's testable entry point (e.g. `runCli` — returns an exit code instead of calling `process.exit`/throwing) must wrap *every* stage of its pipeline in try/catch, not just the stages anticipated to fail, so any unexpected exception still produces the function's normal controlled-failure output (a clean exit code plus a clear stderr message) instead of an uncaught crash. Each such entry point's test suite must include an unexpected-throw case for every stage, not only the stages that already had one. (Evidence: PROGRESS.md 2026-07-18 adversarial-hunt run — `reviewer/src/cli.js`'s `runCli` wrapped `parseArgs`/`execGit`/`loadRulesFn` in try/catch but left `reviewDiffFn`, `formatReport`, and `writeFile` unguarded; a thrown error from any of those three (e.g. `writeFile` failing on a bad `--out` path) crashed the process with a raw stack trace instead of the exit-code-1-plus-stderr-message behavior every other failure path in the same function already had, and no existing test exercised those three stages failing.)


## 4. Timezone-preserving timestamps must be compared numerically

Timestamps that preserve their own timezone offset (e.g. git's `%aI`/`%aD`, or any ISO 8601 string with a non-`Z` offset) must never be sorted or compared with plain string comparison (`localeCompare`, `<`, `>`) — parse to a `Date`/epoch number first and compare numerically, since two such strings can order differently as text than as real instants whenever their offsets differ. Any test suite covering such a sort must include a mixed-offset case (not just all-`Z` or all-same-offset fixtures), since same-offset inputs can pass a string-comparison sort by coincidence and hide the bug. (Evidence: PROGRESS.md 2026-07-18 adversarial-hunt run — `reviewer/src/standup/formatStandup.js` sorted commits with `a.date.localeCompare(b.date)` on `%aI` author-date strings, which keep each commit's original author-timezone offset; a commit at `2026-07-18T23:30:00-07:00` (actually `2026-07-19T06:30:00Z`, later) sorted before one at `2026-07-19T01:00:00+00:00` (`2026-07-19T01:00:00Z`, earlier) purely because `'07-18' < '07-19'` as text. All existing tests used `Z`-only or same-offset fixtures, so the bug shipped undetected.)


## 5. Await all same-shape DI collaborators, not just the ones awaited today

When a function accepts two or more dependency-injected collaborators of the same shape/role (e.g. multiple `collect*`/`fetch*` functions passed via a `deps` object) and awaits one of them, it must await all of them, even if a collaborator's current default implementation happens to be synchronous — the DI seam itself, not today's default, is the contract, and a caller injecting an async replacement for the un-awaited one is a natural, foreseeable usage. Every such multi-collaborator function's test suite must include at least one case where a collaborator that the source treats as "presumably sync" is mocked as `async`, not only the collaborator(s) already awaited. (Evidence: PROGRESS.md 2026-07-18 adversarial bug-hunt run — `reviewer/src/standup/generateStandup.js` awaited `collectPullRequestsFn(...)` but called `collectCommitsFn(...)` without `await`; reproduced directly by injecting an async `collectCommits` mock, which made `commits` an unresolved Promise and crashed `groupByAuthor`'s `for...of` with "commits is not iterable". Dormant in shipped code only because the real `collectCommits` is synchronous; no existing test mocked `collectCommits` as async, so the asymmetry shipped undetected.)


## 6. encodeURIComponent caller-supplied values interpolated into URLs

Any value that flows from a CLI flag or other caller-supplied input into a URL/path built by string interpolation (e.g. a REST API request URL) must be `encodeURIComponent()`-ed at the point of interpolation, never spliced in raw — even when the value "should" be a simple token like a username or an ID, since nothing upstream enforces that shape by the time it reaches the sink. Every such URL-building function's test suite must include a case where one of the interpolated values contains a `/` (or other URL-structural character) and assert the resulting request target is unaffected (still points at the intended path), not just a happy-path case with well-formed values. (Evidence: PROGRESS.md 2026-07-18 adversarial bug-hunt run, post-task-9 — `reviewer/src/github/postReviewComment.js` built its GitHub API request URL as `` `${GITHUB_API_URL}/repos/${owner}/${repo}/issues/${prNumber}/comments` `` with no encoding; `owner`/`repo`/`prNumber` come from `reviewPrCli.js`'s `--owner`/`--gh-repo`/`--pr` flags, which the task-9 `SKILL.md` explicitly expects an agent to fill in from a PR URL rather than a fully-trusted operator typing them. A value containing `/` (e.g. `--owner 'attacker/other-owner'`) silently redirected the POST to a different `api.github.com` path than the one reported in the success message, while still attaching the real bearer token. No existing test covered a `/`-containing interpolated value, so this shipped undetected.)


## 7. CLI value-taking flags must fail loudly on a missing value

A CLI parser's value-taking flag (one that consumes the next `argv` token, e.g. `args.x = argv[++i]`) must fail loudly with a clear "Missing value for --x" error when that next token doesn't exist, never silently assign `undefined` and move on — this is especially dangerous for *optional* flags, where `undefined` (flag given, value missing) is otherwise indistinguishable from the flag never being given at all, so a malformed invocation silently produces different, unexplained behavior instead of an error (required flags are unaffected, since their own "missing required" check already rejects `undefined` the same as absent). Every such parser's test suite must include a case where a value-taking flag is the last token in `argv`. (Evidence: PROGRESS.md 2026-07-18 adversarial bug-hunt run, post-task-10 — `standupCli.js`'s `parseStandupArgs` let `--owner` (an optional flag that gates whether PR data is fetched at all) reach `undefined` when given as the last token, and its pairing check only tested truthiness, so `parseStandupArgs(['--repo', '.', '--owner'])` returned `{ owner: undefined, ... }` with no thrown error — the CLI silently produced a commits-only report with no indication `--owner` had even been seen. The identical shape was reproduced in the three older parsers too: `cli.js`'s and `reviewPrCli.js`'s optional `--out` both silently fell back to printing to stdout instead of writing the file the caller asked for, with no error, when given as the last token.)


## 8. Dynamic report wording must be derived from the actual input

A report/message-formatting function must build any wording that describes a dynamic input (a time window, a count, a scope, etc.) from the actual value it was given, never a hardcoded phrase that only describes the common or default case — even for a "no results" / empty-state branch, which is easy to treat as a fixed string precisely because it has no data of its own to interpolate. If the same output also displays the real value elsewhere (e.g. a `**Since:** <timestamp>` header line), a hardcoded phrase in another part of that output can end up directly contradicting it. Any test suite covering such a message must include a case where the dynamic input differs from the default/common value, not only the no-argument or default-value case — a test that omits the varying input entirely can pass while missing exactly the combination that breaks. (Evidence: PROGRESS.md 2026-07-18 adversarial bug-hunt run, post-task-11 — `reviewer/src/standup/formatStandup.js`'s empty-groups branch unconditionally rendered `'No commits or pull requests in the last 24h.'`, even though `meta.since` (from `standupCli.js`'s arbitrary `--since` flag) could be any window. Reproduced directly: `formatStandupReport(new Map(), { since: '2020-01-01T00:00:00.000Z' })` rendered `**Since:** 2020-01-01T00:00:00.000Z` immediately followed by `No commits or pull requests in the last 24h.` — two adjacent, directly contradictory lines. The existing test for this branch called `formatStandupReport(new Map())` with no `meta` at all, so it never exercised a real `since` alongside an empty result and passed despite the bug.)


## 9. Action-describing status messages must derive from the collaborator's actual return value

A user-facing status/success message that describes *which* of several actions a collaborator took (e.g. "created" vs. "updated") must be derived from that collaborator's actual return value, never hardcoded for only one of those actions — a collaborator whose whole job is to conditionally choose between two or more actions must surface which one it took in its return value (not just the resulting data), so a caller synthesizing a message from that call can be accurate for every branch, not just the one the message happened to be written for. Every such reporting caller's test suite must mock the collaborator with more than one distinguishable return shape (one per action it can take), not only a single fixed canned value — a test that always mocks the same return shape can pass while the message is wrong for every other action, since it never exercises the branch that would expose it. ## 10. Depth-counting boundary derivation must mask strings/template literals/comments

A rule (or any other diff-scanning code) that counts brace/paren depth character-by-character to find a per-occurrence block or statement boundary must first mask out characters that fall inside a string or template literal, OR a `//` line comment, OR a `/* */` block comment — a `{`/`}`/`(`/`)` inside any of these is not real code structure, but a naive per-character count treats it as one anyway, desynchronizing the depth tracker from the boundary it's supposed to find. ## 11. Run all preconditions before committing to a persistent side effect

A request handler that both validates a precondition (input shape, config/secret sanity, permissions) and performs a persistent side effect (a DB write, an external API call that creates a resource) must run every such precondition check before committing to the side effect, never interleave a fallible check in between two writes or after the write it's meant to guard — otherwise a late-failing check leaves an orphaned side effect the client is told never happened, and (worse) if the side effect itself makes a retry of the same request now behave differently (e.g. a uniqueness constraint), the caller can become permanently stuck with no way to complete the original request once the precondition starts failing. This applies even when the precondition check is expected to pass in every normal (non-misconfigured) run — "it never actually fails in practice" is exactly the condition under which a late-checked precondition's ordering bug goes unnoticed. Every such handler's test suite must assert, for the precondition-fails case, that the side effect's collaborator was never called (not only that the HTTP response is the expected error) — asserting on the response alone can pass even when the side effect already fired. ## 12. Exemption/allowlist conditions must check the same matched value, not the whole line/block

A rule's *exemption*/allowlist condition (e.g. "don't flag this if X is also present") must be checked against the same specific value its positive check already matched, never against the whole line/block the positive check merely happened to be scanning — otherwise unrelated text sharing that same line or block (a trailing comment, an `||` fallback, a sibling statement) can satisfy the exemption and silence a genuine finding that has nothing to do with it. Before adding or trusting such an exemption, confirm what would happen to the specific case it claims to protect if the exemption were deleted outright — if the positive check's own pattern already can't match that case for an unrelated structural reason, the exemption is dead weight that only adds a bypass surface, not real protection. Every such exemption's test suite must include a case where the positive pattern matches on genuinely bad input *and* the exemption's trigger text is also present elsewhere on the same line/block (not the exemption's trigger text alone, which only proves the exemption fires, not that it fires narrowly enough). ## 13. Containment/reference checks must use word-boundary matching, not raw substring

A "does this text contain/reference X" check — whether it's a prose "does this text mention X" check or a code-reference check like "does this file's content require/import path X" — must match X as a whole token, bounded by non-word characters (or start/end of string) on both sides (e.g. a `\bX\b`-style regex), never as a raw substring (`String.includes`) — this is especially dangerous for short tokens (2-3 characters) or tokens that are themselves a prefix of a plausible longer identifier, both of which are likely to appear inside unrelated words/paths purely by coincidence, silently satisfying the check without the text actually containing/referencing X at all. This applies even when the token is derived generically (e.g. split from a hyphenated name, or a `dir/basename` path fragment) rather than hand-picked, since a substring-prone token is just as dangerous either way. Every such check's test suite must include a case that proves a false pass is actually prevented — text containing the token only as a substring of an unrelated, longer word/path, with the real, intended reference absent — not only positive cases where the real reference happens to be present. When auditing this repo for this bug class, check every raw `String.includes(...)`/`.indexOf(...)` call used as a containment/reference test, not only ones over free-text prose — the identical shape recurs in path/import-reference matching, not just skill-name mentions. ## 14. A posted marker is not a secret once posted — prefer earliest match, not most recent

A marker/identifier that a tool posts into public or shared output, then later reads back to recognize "this is my own prior content," must not be trusted as a secret credential once it has been posted even once — even if it was originally derived from a secret (e.g. an HMAC keyed by a token) — because anyone who can read the already-posted output can copy that exact marker verbatim onto new content they control, with no need to know (or guess) the secret that produced it; deriving a marker from a secret only raises the bar for producing a *first* forged marker, it does nothing to stop a *copy* of one that already exists. A search that identifies "the real prior occurrence" among several marker-matching candidates by preferring the most recently posted one is exploitable by this copy attack every time: a copy, being a copy, is necessarily posted after the genuine original it copied from, so it always looks "most recent" and permanently displaces the genuine occurrence from all future updates. Prefer the *earliest* matching occurrence instead — a copy can never predate the content it copied, so the first match in chronological order is always the genuine one, and a later copy is simply ignored rather than mistaken for canonical. Every such matching function's test suite must include a case where two candidates share the identical marker (one genuine, one a later copy of the same literal text) and assert the earlier one, not the later one, is the one treated as canonical. (Evidence: PROGRESS.md 2026-07-19 adversarial bug-hunt run, post-task-19 — `reviewer/src/github/postReviewComment.js`'s `findExistingBotComment`, unchanged by task 19's own `computeBotCommentMarker` HMAC work, still walked all matching comments and kept overwriting `found` with each later match, i.e. last-match-wins. Task 19's stated goal was to stop a non-owning PR commenter from spoofing the bot's marker and hijacking future updates; deriving the marker's suffix from an HMAC of the caller's token was believed sufficient because the suffix is "unpredictable to anyone without that credential." That reasoning missed that the marker is posted as plain text at the start of every comment the tool writes, so it is never actually secret once posted — reproduced directly: a genuine bot comment (id 101, real HMAC marker) followed by a second, later comment (id 102) that merely copied that visible marker text verbatim caused `postReviewComment` to `PATCH` comment 102 on the next run instead of 101, with no knowledge of the token required to do so — permanently orphaning the real comment, the exact failure task 19 was written to prevent, defeated by a mechanism (last-match-wins search) inherited unchanged from the pre-HMAC design and never re-examined against the new threat model. Fixed by switching `findExistingBotComment` to return the first (oldest) match and stop searching, since a copy can only be posted after the genuine comment it copies from already exists. 1 new regression test (two same-marker comments, older genuine + newer spoofed copy, asserts the older one is PATCHed) plus 1 existing test's expectation flipped from "most recent wins" to "earliest wins" to match the corrected behavior; both fail against the pre-fix code and pass against the fix.)


## 15. A sanitization fix must be applied to every structurally similar sink

A sanitization fix for attacker-controlled free text interpolated into a generated report/message must be applied to every surface that interpolates the same class of attacker-controlled text, not only the one surface whose bug prompted the fix — introducing (or discovering) a sanitizer for one output format/module does not, by itself, mean a structurally identical sink elsewhere got the same protection; each sink must be checked individually. This is especially important when the surfaces differ in *impact*, not just shape: a sink that only reaches a local file/stdout is a much smaller blast radius than one that gets posted somewhere else can act on it (e.g. rendered as a live link, executed, or trusted by a downstream reader) — and it is exactly the higher-impact sink that's easiest to overlook if the original fix was motivated by, and tested against, the lower-impact one. When adding or reviewing a sanitizer for this reason, grep the codebase for other places that build the same kind of output (other `format*`/`render*` functions, other places a rule's `message`/`fix` field gets interpolated) and confirm each one either already sanitizes or is updated to use the same helper, rather than assuming coverage transfers. (Evidence: PROGRESS.md 2026-07-19 adversarial-hunt run 5 — `reviewer/src/standup/formatStandup.js`'s `sanitizeMarkdownText` was added specifically because commit messages and PR titles are attacker-influenceable, but `reviewer/src/format/markdownReport.js` — a structurally identical markdown-report builder whose `issue.message`/`issue.fix` fields routinely embed diff-controlled content verbatim (e.g. `security.js`'s hardcoded-credential finding quotes the offending added line) — kept splicing that content into markdown completely unescaped, and went unnoticed through four prior adversarial-hunt rounds. Reproduced directly, then fixed by extracting `sanitizeMarkdownText` into a shared `reviewer/src/utils/sanitizeMarkdownText.js` and applying it to `file`/`message`/`fix` in `markdownReport.js`, with `formatStandup.js` switched to import the same shared helper instead of keeping its own copy.)


## 16. Escape-character-based sanitizers must escape the escape character itself

A function that neutralizes structural characters in free text by matching a fixed set of characters and prefixing each occurrence with an escape character (e.g. backslash-escaping markdown) must include the escape character itself in the matched set — omitting it lets a value that already contains that escape character adjacent to one of the target characters flip the total escape-run parity once the sanitizer's own inserted escape character is added, leaving the target character live/unescaped instead of neutralized. This is invisible to a spot-check against clean input (no pre-existing escape characters) and only shows up once the input already contains the escape character itself, which attacker-controlled diff/commit content routinely does (a quoted source line can legitimately contain a literal backslash). Concretely, for backslash-based markdown escaping: CommonMark backslash-escapes are resolved by scanning left-to-right and greedily pairing each backslash with the very next character; a sanitizer that escapes `*` but not `\` turns an input's existing single backslash before `*` (`\*`, 1 backslash) into 2 backslashes before the asterisk once its own escape is inserted — an even count, which pairs off entirely among themselves and renders as one literal `\`, leaving the `*` freshly unescaped and structurally live. Escaping the escape character too keeps the total backslash run before any target character odd (original N backslashes, each individually escaped to 2, plus 1 more for the target character itself = `2N+1`, always odd), which always pairs off with, and neutralizes, that character regardless of how many escape characters preceded it in the input. Every such sanitizer's test suite must include a case where the input already contains the escape character immediately before one of the other target characters, not only clean input with no pre-existing escape characters, and should assert no even-length run of the escape character sits directly before an unescaped target character in the output. (Evidence: PROGRESS.md 2026-07-19 adversarial-hunt run 6 — `reviewer/src/utils/sanitizeMarkdownText.js`, added in the immediately preceding run (adversarial-hunt run 5) specifically to neutralize attacker-controlled markdown before it reaches a live GitHub PR comment, escaped `` ` * _ [ ] ( ) `` but not `\` itself. Reproduced directly with a markdown renderer (`marked`): input `note: \*ALERT\* click here` (a plausible diff-quoted line already containing backslash-escaped asterisks) sanitized to `note: \\*ALERT\\* click here`, which rendered as `note: <em>ALERT</em> click here` — live emphasis formatting, not the inert literal text the function's own docstring promised, on the exact GitHub-PR-comment surface the run-5 fix was written to protect. The specific `[text](url)` clickable-link shape from run 5's own reproduction happened to stay blocked in this report's format regardless (the sanitizer always inserts a backslash immediately before every `(`, which breaks the `]`-immediately-followed-by-`(` adjacency CommonMark's link syntax requires, independent of parity), but the underlying escaping guarantee was still broken for every other structural character. Fixed by adding `\\` to the escaped character class in `sanitizeMarkdownText.js`; 1 new regression test (pre-escaped input, asserts the fully-escaped odd-parity output and that no unescaped target character survives), verified to fail against the pre-fix code and pass against the fix. `reviewer/` suite green throughout (275 -> 276); `sample-app/` unaffected (48/48).)


## 17. Boundary-walk continuation checks must not terminate on blank/comment-only lines

A statement-boundary or brace-body-boundary walk that decides a multi-line construct has ended by checking whether the current line is a valid continuation of the previous one (e.g. "starts with `.`" for a chain, or "isn't a continuation" as the signal a signature-then-later-brace statement is done) must treat a blank or comment-only line (i.e., one that masks to nothing but whitespace) as a non-terminating continuation, never as proof the construct ended — real, valid formatting routinely puts an explanatory comment or a blank line between two lines that are still part of the same construct (a `.then()`/`.catch()` chain with a comment between the two calls; an arrow function's signature and its own opening `{` on a later line, with a comment in between), and a check whose continuation test is "this line starts with `.`" has no way to say yes for a comment/blank line, so it wrongly signals "ended" and truncates the walk before the construct's real remainder is ever scanned. Every such boundary-walk's test suite must include a case with a comment-only (or blank) line inserted between two lines that are still part of the same construct, not only tightly-adjacent-line fixtures — a test that never puts anything between two real lines of the same construct cannot catch this shape. (Evidence: PROGRESS.md 2026-07-19 "self-scheduled routine run 3" entry — `reviewer/src/rules/errorHandling.js`'s `collectStatement`/`handlerHasBraceBody` (both continuation-tested via `!masked.trim().startsWith('.')`) treated a comment-only line the same as a genuinely unrelated next statement, ending the scan right there. ## 18. Existence-detection regexes must run against comment-masked source

A regex used to *detect whether a code construct exists at all* (not to bound an already-known occurrence) must be matched against comment-masked source, never raw source — a commented-out/dead-code occurrence (e.g. `// router.delete('/:id', remove);`) satisfies the same regex as a live one, and a raw match can't tell dead code from live code. Unlike the depth-counting and collected-block keyword-presence guidelines above, string literal *contents* must stay intact here (mask comments only, not strings), since the detection regex's own capture groups routinely need the literal string value (e.g. a route's path). Every such detection regex's test suite must include a case where the pattern's own literal text appears only inside a comment, with the real occurrence (if any) absent or elsewhere. (Evidence: PROGRESS.md 2026-07-19 "self-scheduled routine run 7" entry — `reviewer/src/docDrift/parseExpressRoutes.js`'s `METHOD_CALL_PATTERN`/`ROUTE_CALL_PATTERN`/`MOUNT_PATTERN`/`REQUIRE_PATTERN` all matched raw `source` text with no comment-awareness; first flagged as an open question in the "self-scheduled routine run 3" entry and restated unresolved across the six following runs. Reproduced directly: a commented-out `router.delete('/:id', ...)` was extracted as a live DELETE route, and a commented-out `app.use('/api/secret', secretRoutes)` mount was resolved as a live mount — either shape silences a genuine doc-drift finding for a route documented in `openapi.yaml` but actually removed from code. ## 19. Clarification: maskComments vs full maskStringLiterals, and single-line scope

Clarification on the two masking guidelines directly above: they differ by whether the check's own regex has capture groups that need string *content* intact (comment-only `maskComments`, e.g. `parseExpressRoutes.js` capturing a route's quoted path) or not (full `maskStringLiterals`, comments and strings both — a plain presence/absence check has nothing to capture from a string, so a string merely mentioning the marker is exactly as spurious a match as a comment mentioning it). This applies at single-diff-line scope too, not only to a `collectBoundedBlock`-style multi-line window — `reviewer/src/rules/style.js`'s `CONSOLE_LOG` check matched one raw `collectAddedLines` line directly, so an added string literal `"call console.log(x) to debug"` (no real, executing call) was flagged as leftover debug code; fixed with `maskStringLiterals` applied per-line (fresh `quoteState = null`, since a single diff line has no visibility into a preceding line's open string state). (Evidence: PROGRESS.md 2026-07-19 "self-scheduled routine run 8" entry.)


## 20. Keyword-presence checks on a collected block must test masked text

A check that tests a *collected* multi-line block or statement window for the presence (to flag) or absence (to require) of a specific keyword/marker (e.g. `try {`, `asyncHandler`, `.catch(`, `await`) must test the string/comment-masked version of that collected text, never the raw text — a comment or string literal that merely *mentions* the marker (a TODO saying "wrap this in try {} catch", a log message containing the literal word "await") satisfies a naive raw-text regex exactly as if the marker were real code, producing a false negative for a "flag if X is missing" check or a false positive for a "flag if X is present" check. This is the same masking discipline the string-literal-aware depth-counting guideline above already requires for brace/paren counting, applied to a second, independent consumer of the masked text within the same collected block: not just "is this character real structure" but "is this keyword real code" — collecting the block's boundary correctly (per that guideline) does not, by itself, protect a keyword-presence check run against the raw content of that same block. Every such check's test suite must include a case where the required/forbidden marker's own literal text appears only inside a comment (or string literal) somewhere in the collected block, with no real occurrence anywhere else, and assert the check still reaches the correct verdict. (Evidence: PROGRESS.md 2026-07-19 "self-scheduled routine run 3" entry — `reviewer/src/rules/errorHandling.js`'s `TRY_BLOCK`/`ASYNC_WRAPPER`/`CATCH_CALL` checks and `reviewer/src/rules/performance.js`'s `AWAIT_PATTERN` check all ran their regex against the raw block/window text returned by `collectBoundedBlock`/`collectStatement`, not the masked text those same helpers already compute internally for their own depth-counting. Reproduced directly, three ways: an async handler with a body containing only `// TODO: wrap this in try { ... } catch (err) { ... }, or use asyncHandler` (no real try/catch) was not flagged as missing error handling; `job.then(doA); // should really add a .catch(handleA) here later` (no real `.catch()`) was not flagged as uncaught; and a clean `.forEach((item) => { // do not await here, keep this synchronous \n processSync(item); })` (no real `await`) was incorrectly flagged as using `await` inside a forEach. All three predate this run's own earlier fix in the same session (confirmed unaffected by it) and were never caught because none of these checks' existing tests put the marker's literal text inside a comment. Fixed by calling `maskStringLiterals` once more on the already-collected `block`/`window` string at each of the three call sites (two in `errorHandling.js`, one in `performance.js`) and testing the regex against the resulting masked text instead of the raw one. 3 new regression tests (one per call site), confirmed via `git stash` to fail against the pre-fix code and pass against the fix. `reviewer/` suite 288 → 294 green (6 net-new across both new guidelines' fixes); `sample-app/` unaffected, 48/48.)


## 21. Recursive visited-tracking must be scoped per root-to-node path

A recursive tree/graph walk that guards against infinite loops by tracking "visited" nodes must scope that tracking to the current root-to-node path, not share one mutable set across the whole traversal — otherwise a node legitimately reachable via two independent branches (not a real cycle) is treated as already-visited the second time, and its results are silently dropped. Pass each recursive call its own extended copy of the ancestor set (or add-before-recurse/remove-after-return) instead of mutating one shared set in place. Test coverage must include both a genuine cycle case and a same-node-reached-via-two-different-branches case. (Evidence: PROGRESS.md 2026-07-20 adversarial-hunt run — `reviewer/src/docDrift/collectExpressRoutes.js`'s `visited` Set was shared by reference across the entire recursive mount-walk to guard require cycles, but this also fired on the ordinary pattern of mounting the same router file under two prefixes (e.g. API versioning), silently dropping the second mount's routes and producing a false-positive doc-drift "missing from code" finding for routes that are actually implemented. No existing test exercised a router required from two mount points. Fixed by passing each recursive call a fresh ancestors set — current path plus this file — instead of one Set mutated by reference throughout the walk.)


## 22. Fix every sibling detection-regex in the same rule module, not only the one that triggered the fix

A masking fix (or any other correctness fix) applied to one pattern-presence/detection check in a rule module must be checked against every other presence/detection check in that same module operating on the same line/block data, not only the specific check whose false positive or false negative prompted the fix — sibling checks sharing the same file, the same unmasked-vs-masked distinction, and the same input shape are exactly as likely to carry the identical bug, and a fix scoped to just the reported case leaves the others live until independently rediscovered. This generalizes guideline 15's "fix every structurally similar sink" principle (stated for sanitization sinks) to detection-regex checks specifically — a distinct, separately-evidenced failure mode, not a broadening of 15's own wording. Every such fix's own PROGRESS.md entry should note which sibling checks in the same module were audited and why any left unchanged are judged not the same bug class, not merely why the one that was fixed needed fixing. (Evidence: PROGRESS.md 2026-07-20 "adversarial hunt run, requested by Vijay — recent-commits bug hunt" entry — `reviewer/src/rules/performance.js`'s `check()` had three raw-line pattern checks in the same function scope: `FOREACH_START`, `AWAIT_PATTERN`, and `DEEP_CLONE_ANTIPATTERN`. Only `AWAIT_PATTERN` had previously been fixed to run against `maskStringLiterals`-masked text (guideline 20); its two siblings, sitting in the very same function, still tested raw `line.content`. Reproduced directly: a comment merely mentioning `JSON.parse(JSON.stringify(...))` was flagged as the deep-clone anti-pattern itself, and a comment merely describing old `.forEach()` syntax was treated as a real forEach start — `collectBoundedBlock` then walked into unrelated following async code, found its real but unrelated `await`, and misattributed it to the fake forEach at the comment's line, a false positive against fully compliant code. Fixed by masking both siblings the same way `AWAIT_PATTERN` already was; 2 new regression tests, confirmed to fail pre-fix and pass post-fix. `reviewer/` suite 316 → 318 green throughout; `sample-app/` unaffected, 49/49. Traced `security.js`'s equally-unmasked `SECRET_PATTERN`/`EVAL_PATTERN` but left them as-is on the judgment that a security scanner should still flag a secret/eval literal sitting inside a comment rather than exempt it — a deliberately different design choice, not an instance of this bug class.)


## 23. AST subtree searches must stop at nested-function boundaries

An AST subtree search answering "does the occurrence being checked contain X" (a try/catch, a chained `.catch()` call, an `await`) must stop at a nested function's own boundary, never descend into it — a nested function's own try/catch, chained `.catch()`, or await belongs to that inner function's own separate execution, not the outer handler/statement/callback being checked. This generalizes guideline 2's "a boundary must be derived from real structure, never aggregated beyond the actual occurrence" principle to function scope, for the AST-based boundary derivation path (task 23's AST spike) as opposed to the brace/paren-depth-counting regex path guideline 2 originally covered. Every such search's test suite must include a nested, unrelated function defined and called inside the occurrence, containing X itself, for both a false-negative-prone check (try/catch, catch-call) and a false-positive-prone one (await). (Evidence: PROGRESS.md 2026-07-20 "adversarial hunt run, requested by Vijay — Task 23 AST spike review" entry — `errorHandling.js`'s `subtreeHasTryStatement`/`subtreeHasCatchCall` and `performance.js`'s `subtreeHasAwait`, added by the immediately preceding commit (`f7c6ddc`, "Task 23: AST spike"), each walked a node's entire subtree via `walk.full` with no nested-function-boundary awareness. Reproduced two real bugs with standalone scripts before touching any code: an outer async route handler with no try/catch of its own went unflagged because an unrelated nested helper function had its own try/catch (false negative — `errorHandlingRule.check()` returned `[]` for a genuinely unguarded handler); and a `.forEach()` callback that never itself awaits was flagged anyway because it defines and calls a separate nested async helper that does await (false positive against fully compliant code). Fixed by extracting `reviewer/src/utils/subtreeInOwnScope.js`, a `walk.full` seeded with a custom traversal base where `FunctionDeclaration`/`FunctionExpression`/`ArrowFunctionExpression` are visited but never descended into, and rewiring all three call sites. Verified a legitimate same-statement `.then().catch()` chain (`.catch()` chained directly onto the outer promise, not nested inside a callback body) is still correctly detected — the main risk of the fix, confirmed via a dedicated test. 4 new regression tests; `reviewer/` suite 333 → 337 green throughout; `sample-app/` unaffected, 49/49. Scoped the fix to the AST path only — the older regex/text-boundary fallback path has an equivalent inherent weakness but fixing it there would require hand-rolling function-boundary detection, exactly the complexity the AST path exists to sidestep; left as a known limitation of the documented-fallback-only regex path per RW1.)


## 24. A new numbered guideline must land its docs/GUIDELINES_HISTORY.md entry in the same commit

A commit that appends a new numbered entry to CLAUDE.md's compact GUIDELINES list must append that same-numbered entry's full recurrence narrative to `docs/GUIDELINES_HISTORY.md` in the same commit — not as separate, deferrable follow-up work. The compact list's own header states the contract this guideline exists to enforce: "full recurrence narratives ... live verbatim in `docs/GUIDELINES_HISTORY.md`, same numbering ... this list is a lookup index, not the complete rationale." A guideline number with no matching history entry breaks that promise silently: nothing in CLAUDE.md itself flags the gap, since the compact entry reads as complete on its own, and the omission is invisible unless someone actually opens the history file looking for the numbered section and finds it isn't there. ## 25. Masking utilities must preserve embedded newlines for whole-file callers

A masking utility that blanks string/template-literal or comment content to same-length spaces (`maskStringLiterals`, `maskComments`) must preserve an embedded newline character as a newline in its output, not flatten it to a space — even though a space is visually "same length" and doesn't disturb brace/paren-depth counting or keyword-presence regexes, a caller that derives a line number by counting `\n` characters in the masked text (rather than masking one diff line at a time, the pattern every existing rule-module caller uses) silently undercounts every line number computed from text after a multi-line string or block comment whose own embedded newlines got swallowed. This bug class is invisible to any caller that masks per-line (a single diff line's own content never contains an embedded `\n` to begin with, so the flattening has nothing to flatten) and only manifests for a caller passing a whole multi-line file as one `content` string — exactly the shape `docDrift/parseExpressRoutes.js` already documents as a supported use case (its own header comment cites "callers that pass a whole multi-line file as a single `content` string"), but until task 25 added `findUnparsedRoutes`, nothing in this codebase actually derived a *line number* from that whole-file-masked text; every pre-existing whole-file caller only tested regex presence/absence or walked character positions directly, never converted a match index into a reported line. Every masking-utility test suite must include a whole-file, single-call case spanning a multi-line block comment or multi-line template literal, asserting both the documented same-length invariant and a matching `\n` count between input and masked output — not just the per-line-threaded-across-calls case the existing `quoteState`-threading tests already cover. (Evidence: PROGRESS.md 2026-07-21 adversarial-hunt run — reproduced directly: a source file with a 3-line `/* ... */` block comment followed by `router.get(\`/widgets/${id}\`, getWidget);` on line 7 caused `findUnparsedRoutes` to report the finding at line 4 instead of line 7, because `maskComments`'s `/* */` branch appended a single space per masked character regardless of whether that character was itself a newline, merging the comment's 3 source lines into 1 inside the masked text `lineNumberAt` then counted `\n` characters in. The identical flattening existed in `maskStringLiterals`'s block-comment branch, its quote-content branch (a multi-line template literal's own embedded newlines), and its backslash-escape branch (a line-continuation escape's own newline) — confirmed with a standalone reproduction (`const x = \`line1\nline2\nline3\`;\nrouter.get(\`/x\`);` masked to only 1 `\n` instead of 3) before touching any code, even though no current caller of `maskStringLiterals` on a multi-line template literal yet derives a line number from the result (only `findUnparsedRoutes`'s `maskComments` call does today) — fixed proactively in both functions since the same bug class would recur the moment any future caller does. Fixed by adding a shared `blank(ch)` helper (`ch === '\n' ? '\n' : ' '`) and routing every single-character space-append through it in both functions' block-comment, quote-content, and backslash-escape branches; the two-character literal masks for `/*`, `*/`, and the block-comment-open sequence were left untouched since those characters (`/`, `*`) can never themselves be a newline. 4 new regression tests (2 in `maskStringLiterals.test.js` covering both functions' whole-file multi-line cases, 1 end-to-end in `parseExpressRoutes.test.js`'s `findUnparsedRoutes` describe block reproducing the exact line-4-vs-7 misreport, 1 more for the template-literal case), each confirmed to fail against the pre-fix code (via a temporary revert of just the source file, not `git stash` of the whole tree) and pass against the fix. Reran the pre-existing per-line-threaded `quoteState` tests unchanged to confirm the fix doesn't disturb that calling pattern — it doesn't, since a single line's own content has no embedded `\n` for `blank()` to ever branch on. `reviewer/` suite 363 → 367 green throughout; `sample-app/` unaffected, 50/50.)
