Diff-scanning static-analysis rules (in `reviewer/src/rules/*` and, later, `review-rules.yaml`) must scope pattern checks to the local block/occurrence being evaluated, never aggregate a single boolean across a whole file diff OR across multiple files in the same diff — one compliant instance (a try/catch, a `.catch()`, a matching test file) must not silence findings for a different non-compliant instance, whether in the same file or a different file changed in the same diff. This violation isn't only the obvious `hasX`-computed-once-and-reused shape — a single regex `.test()`/match against a *joined/combined multi-line string* of all added lines (e.g. `lines.map(l => l.content).join('\n')`) is the same violation wearing a different shape, since it lets an occurrence in one block satisfy (or get blamed for) a pattern that actually belongs to a different, unrelated block. Any check that needs to reason across multiple lines of one occurrence must extract that occurrence's own bounded block first (e.g. brace-depth tracking from its opening `{` to its matching `}`, as `errorHandling.js` and the `performance.js` fix below do) before testing it — never regex a same-file-wide joined blob. Every such rule's test suite must include a multi-occurrence case (2+ handlers/chains/blocks in one file, or 2+ source files in one diff, mixed compliant/non-compliant) — a single-occurrence test cannot catch this class of false negative, and when auditing an existing rule for this bug class, explicitly check for `join('\n')`/combined-string regex tests, not just reused boolean flags. Extracting a bounded per-occurrence block is necessary but not sufficient: the block's boundary itself must be derived from the code's actual structure (brace depth, paren depth, or a statement-terminating `;`), never an arbitrary fixed-size line window — a window that's too small can miss a real `.catch()`/`try`/etc. that's genuinely part of the same occurrence a few lines further down (false positive), while a window that's too large can pull in an unrelated, independent occurrence's compliant marker and silence a genuinely non-compliant one right next to it (false negative). "The next occurrence's own start" (e.g. the next handler signature, the next `.route()` call) is *not* a safe substitute for the occurrence's own structural end unless something already guarantees nothing else can appear in between — real code regularly has unrelated statements, helper functions, or other non-occurrence content sitting between two occurrences of the same construct, and using the next occurrence's start as a boundary sweeps that unrelated content's own compliant markers (e.g. its own unrelated try/catch) into the current occurrence's block, silencing a genuinely non-compliant occurrence. Prefer the occurrence's own brace/paren-depth end every time one exists; only fall back to "next occurrence's start" when the construct genuinely has no structural closing token of its own to track. Every such rule's test suite must therefore include both a multi-line-formatted-but-compliant case (to catch the too-small-window false positive) and an adjacent-independent-occurrences case with *unrelated, non-occurrence content* in between (to catch both the too-large-window false negative and the next-occurrence's-start false negative), not just a same-line-or-tight-window case or two occurrences with nothing but whitespace between them.
