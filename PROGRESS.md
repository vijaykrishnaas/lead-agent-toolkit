- **Real bug found and fixed — `formatStandupReport` sorted commits by lexicographic string comparison of timezone-offset-preserving timestamps, misordering commits across timezones:** `reviewer/src/standup/formatStandup.js` sorted each author's commits with `[...commits].sort((a, b) => a.date.localeCompare(b.date))`. `commit.date` comes from `collectCommits.js`'s `git log --pretty=format:...%aI...` — git's strict-ISO-8601 author date, which preserves each commit's *own* author-timezone offset rather than normalizing to UTC. String comparison of such timestamps does not track real chronological order when offsets differ. Reproduced directly: a commit dated `2026-07-18T23:30:00-07:00` (an actual UTC instant of `2026-07-19T06:30:00Z`, i.e. later) sorted *before* one dated `2026-07-19T01:00:00+00:00` (`2026-07-19T01:00:00Z`, earlier) purely because `'2026-07-18' < '2026-07-19'` as text — confirmed with a standalone Node repro before touching any code. This is a real, plausible failure mode for a tool whose entire purpose is "here's what each author did, in order" for a team with contributors across timezones (or even one author who commits from machines in different timezones, or across a DST change).
  - Fix: changed the sort comparator to `new Date(a.date) - new Date(b.date)` (numeric epoch comparison), which is timezone-offset-agnostic.
  - Added 1 regression test to `tests/standup/formatStandup.test.js` using offsets that straddle a UTC day boundary. Caveat worth recording: my first draft of this test used offsets that *didn't* straddle a day boundary and passed even against the pre-fix buggy code by coincidence (the hour digits alone happened to sort correctly) — I only caught this by deliberately running the new test against the old source before trusting it, which is why the fix is confirmed with an explicit fail-before/pass-after check, not just "tests are green."
